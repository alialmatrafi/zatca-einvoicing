# Phase 1 — Generation (effective since 4 December 2021)

Applies to **every** VAT-registered taxable person resident in KSA, with no wave/threshold — this has been mandatory for all of them since the effective date. There is no opt-out based on company size, sector, or whether the taxpayer is an establishment or a freelancer under a freelance license.

## Core requirements

1. **Electronic generation only.** Invoices must be generated by an electronic system from the moment of issuance. Scanning or photocopying a handwritten/typed paper invoice does not count as an e-invoice.
2. **Any electronic format is acceptable in Phase 1.** XML is not mandated yet (that's a Phase 2 requirement) — a compliant system could generate a structured PDF, or any format that captures the required fields, as long as it's produced electronically and archived.
3. **All mandatory fields present**, per Article 53(5) of the VAT Implementing Regulation and Resolution Annex 2 — see `invoice-fields.md`. Missing fields make the invoice non-compliant even if it "looks like" a proper invoice.
4. **Anti-tampering controls**, specifically:
   - A locked, sequential invoice counter — no reuse or skipping of reference numbers without a traceable reason (e.g., voided invoices still logged).
   - Protected issue date/time — the system, not the user, sets and locks the timestamp.
   - No silent deletion — an issued invoice can never simply disappear; corrections must go through credit/debit notes.
5. **QR code on every Simplified Tax Invoice** (not required on Tax Invoices in Phase 1). The QR is Base64 TLV-encoded and contains, at minimum:
   - Seller name
   - Seller VAT registration number
   - Invoice timestamp
   - Invoice total (with VAT)
   - VAT amount
   This is the 5-tag TLV structure — see `scripts/zatca_qr_tlv.py` for a working implementation. It must be scannable and verifiable via ZATCA's official mobile app. The TLV length byte is a byte-length, not a character-length — this matters a lot for Arabic seller names (each Arabic character is 2 bytes in UTF-8), and getting it wrong produces a QR that looks fine in testing with English data and silently breaks on real Saudi business names. See the "single most common TLV bug" note in `phase2-integration.md` — it applies equally here.
6. **No cryptographic stamp and no device/solution registration required in Phase 1** — that's introduced in Phase 2. Don't over-build Phase 1 with Phase 2 machinery unless the user is already known to be in scope for their Phase 2 wave; it's fine (and often smart) to build the data model so Phase 2 fields slot in later, but don't block a Phase 1-only launch on Phase 2 infrastructure.
7. **Archiving.** Invoices must be retained per standard VAT record-retention rules (generally the same retention period as other VAT records — confirm the current statutory period, as retention rules are set at the regulation level, not the e-invoicing rules specifically) with a traceable naming/reference convention (VAT number + timestamp + sequential reference is the common pattern ZATCA guidance recommends).

## What "compliant" looks like in code terms

A minimally compliant Phase 1 system needs: a server-side (not client-editable) invoice numbering sequence, immutable storage of issued invoices (append-only, corrections via new credit/debit note records rather than UPDATE/DELETE on the original row), all Annex 2 fields captured at creation time, and QR generation for any invoice flagged as "Simplified" (B2C, or B2B under SAR 1,000). None of this requires calling out to ZATCA — Phase 1 is purely about how the taxpayer's own system generates and stores invoices.
